# 감시 규칙 — 「놓친 것」을 대신 세는 문서

시간이 지나면 조용히 썩는 것들이 있다. 사람은 매일 보는 것에 눈이 미끄러진다.
**이 섹션의 목적은 "내가 안 챙긴 게 뭔가"를 대신 세는 것이다.**

감시는 **판단이 아니라 산수**다. `poll.py` 가 결정론적으로 계산한다.
이 문서는 **규칙과 의도**를 정의한다. 계산·저장 형식은 스크립트 쪽 계약(`CONTRACT.md`)을 따른다.

## 규칙

| # | 규칙 | 등급 | 집계 단위 |
|---|---|---|---|
| W1 | **배포일 경과** — 배포일이 지났는데 티켓이 미완료 | 🔴 | (프로젝트, 버전) |
| W2 | **배포일 임박** — 배포일까지 ≤3일인데 티켓이 미완료 | 🔴 | (프로젝트, 버전) |
| W3 | **QA 시작 경과** — QA 시작일이 지났는데 상태가 아직 개발 단계 | 🔴 | (프로젝트, 버전) |
| W4 | **미처리 ⚠️ 방치** — 미처리 `⚠️` 가 3일↑ (7일↑ 이면 🔴) | 🟡 | 티켓 |
| W5 | **문의 무응답** — 문의 후 3일↑ 답이 없음 | 🟡 | 티켓 |
| W6 | **blocked 장기화** — `blocked: true` 가 7일↑ 유지 | 🟡 | 티켓 |
| W7 | **티켓 정체** — 변화 없이 14일↑ | 🟡 | 티켓 |
| W8 | **배포대기 적체** — 배포대기 상태가 30일↑ | 🟡 | 티켓 |

임계값(`3`·`7`·`14`·`30`)은 **`config.toml` 의 `[watch]`** 에서 읽는다. **코드에 박지 마라.**
임계값을 바꿔야 감시가 사람의 리듬에 맞춰진다. 코드 수정이 필요하면 아무도 안 바꾼다.

## 집계 단위 — 원인이 하나면 알림도 하나다

W1~W3 은 릴리즈 단위 사건이다. **(프로젝트, 버전) 으로 묶어 한 줄로 낸다.**

```
- **[shop 3.2.0]** 배포일 09-03 경과 · 6일째 · <…|WPQ-17676> 외 26건이 아직 Ready to Deploy
```

이전 구현은 티켓마다 한 줄을 뽑아 **릴리즈 하나를 27줄로 도배했다.**
27줄이 말하는 것은 "배포일이 지났다" 한 문장이다. 대표 티켓 1건 + 나머지 개수로 접는다.

W4~W8 은 티켓 단위 사건이므로 티켓별로 센다. 다만 아래 「반복 억제」가 걸린다.

## 해소 마커는 `✅` 다

미처리 판정은 **줄 끝에 `✅` 가 있는지**로 가른다.

```markdown
- `09-04 09:37` ⚠️ **Confluence** `5919834330` v26 → v44 ✅ 변경 대응 2026-09-04 에 정리   ← 해소
- `09-08 16:07` ⚠️ **Confluence** `5919834330` v47 → v48                                  ← 미처리
```

**`→` 를 해소 마커로 쓰지 마라.** `→` 는 이벤트 본문에 이미 쓰인다 (`v26 → v44`, `개발 준비 → 진행 중`).
`→` 로 판정하면 **모든 변경 줄이 해소로 잡혀 W4 가 영원히 0건**이 된다. 실제로 그럴 뻔했다.

나이는 줄 앞의 `MM-DD` 로 센다. 연도가 없으므로 오늘 기준 가장 가까운 과거 연도로 읽는다.

## 반복 억제 — 이게 핵심이다

254일짜리 티켓을 매일 11줄로 보여주면 **3일 만에 안 읽게 된다.** 그러면 감시가 없는 것만 못하다.

`_state.json` 의 `watch` 키에 **처음 걸린 날짜**를 기록한다.

```json
"watch": { "WPQ-15228": { "W8": "2026-09-04" }, "CWEB-1549": { "W7": "2026-09-04" } }
```

| 상황 | 표시 |
|---|---|
| **새로 걸린 것** | 개별 줄로 전부 표시 (`신규 ·`) |
| **이미 걸려 있던 것** | 규칙별 **집계 한 줄**로 접음 (`누적 ·`) |
| **월요일** | 접힌 것도 전부 펼침 — 주 1회는 직면한다 |
| 🔴 등급 | **접지 않는다.** 매일 개별 표시 |

해소되면 `watch` 에서 지운다. 다음에 다시 걸리면 「새로 걸린 것」으로 뜬다.
지우지 않고 남겨두면 해소된 것이 계속 누적 집계에 섞인다.

## `watch_ignore` — 의도적 대기는 방치가 아니다

티켓 md frontmatter 에 **이유와 함께** 적으면 감시에서 제외한다.

```yaml
watch_ignore:
  - rule: W8
    reason: "3.2.0 배포 트레인 대기 — 09-17 일괄 배포 예정"
    until: 2026-09-17
```

- **`reason` 없는 `watch_ignore` 는 무시한다.** 이유를 못 쓰겠으면 그건 방치다
- `until` 이 지나면 다시 감시 대상이 된다. 영구 제외는 없다
- 규칙 번호를 명시한다. 티켓 전체를 감시에서 빼지 마라

"방치"와 "의도적 대기"는 다르다. 이 구분이 없으면 사람은 감시를 통째로 끈다.

## 실측 감각 (2026-09-04 기준)

지금 임계값으로 걸리는 규모:

- W8: **11건** (WPQ-15228 254일, 디자인QA 9건 128~129일)
- W7: WV2Q-53784 46일, CWEB-1549 22일, CWEB-1550 21일
- W1: shop 3.2.0 배포일 09-03 경과, WPQ 27건이 아직 Ready to Deploy

W8 이 11건이므로 **반드시 접어야 한다.** 안 접으면 브리핑이 매일 같은 11줄로 시작한다.

## 하지 말 것

- **사람이 이미 아는 걸 반복해서 알리지 마라.** 그게 알림 피로다
- **"확인이 필요합니다" 로 끝내지 마라.** 며칠 됐는지, 무엇이 걸려 있는지를 **숫자로** 적는다
- **규칙에 없는 걸 "느낌상 걱정된다"고 넣지 마라.** 감시는 산수다.
  새로 챙길 게 생겼으면 W9 를 이 표에 추가하고 임계값을 `[watch]` 에 넣어라
