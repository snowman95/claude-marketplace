# decision-apply

## 목적

결정은 Slack 이 아니라 **daily 파일의 `↳ 답:` 줄**로 들어온다 (봇이 발신 전용이라 스레드를 읽지 못한다).
그 한 줄을 **티켓 md 의 영구 기록으로 옮기고**, 결정이 작업을 풀어주면 **구현까지 이어가는** 것이 이 스킬이다.

답이 daily 파일에만 남아 있으면 다음 주에 아무도 못 찾는다. `## 결정 사항 (Decision Log)` 이 정본이다.

## 호출

```
/decision-apply --date YYYY-MM-DD
```

`--date` 를 생략하면 오늘. 폴링이 `↳ 답:` 이 채워진 것을 감지하면 자동으로 띄운다.

## 경계

- **Jira 쓰기 금지. `git push` 금지. PR 생성 금지.**
- **사람이 쓴 섹션을 수정·삭제하지 않는다.** Research·Plan·문의·Blocked 는 그대로 둔다
- **기존 결정(D-NN)을 삭제하지 않는다.** 대체될 뿐이다
- **답에 담긴 것만 옮긴다. 추측으로 살 붙이지 마라**

## Step 1: 응답된 결정을 모은다

**최근 7일** 브리핑(`{vault}/daily/{날짜}.md`)의 `## 네가 할 일 › 결정` 을 읽는다.
`↳ 답:` 뒤에 내용이 있는 항목만 대상이다. 빈칸은 미응답이므로 건너뛴다.

결정 id 는 **`{날짜}#{번호}`** 다 — `2026-09-09#1`. 번호는 브리핑의 항목 번호 그대로다.

7일을 보는 이유: 사람이 금요일 브리핑에 월요일 답을 달 수 있다. 하루만 보면 그 답을 놓친다.

## Step 2: 아직 기록되지 않은 것만 고른다

`_state.json["decisions"]` 에서 **`applied` 키가 없는 것만** 처리한다.

```json
"decisions": {
  "2026-09-09#1": {
    "ticket": "CWEB-1547",
    "question": "쿠폰 중복 시 배송비 산출 기준",
    "answered_at": "2026-09-09T14:07:00+09:00",
    "answer": "A 로 갑니다"
  }
}
```

`applied` 가 이미 있으면 건너뛴다. **브리핑 줄의 `✅ D-NN 기록` 마커도 같은 역할의 가드다** (Step 3-4).
둘 중 하나라도 있으면 재기록하지 않는다.

## Step 3: 결정마다 처리

### 3-1. Decision Log 에 기록

티켓 md 의 `## 결정 사항 (Decision Log)` 에 **다음 D 번호**로 추가한다.
기존 마지막 번호 + 1. 번호를 재사용하지 마라.

기존 결정을 뒤집는 결정이면 제목에 **`(D-NN 대체)`** 를 붙인다.
**대체된 항목은 삭제하지 않는다** — 왜 뒤집혔는지가 다음 사람에게 필요한 정보다.

형식은 **실제 예시를 따라라**:
`~/Library/Mobile Documents/com~apple~CloudDocs/Documents/projects/web_weverseshop/tasks/shop3.3.0/CWEB-1547.md` 의 **D-01**.

골격은 이렇다.

```markdown
### D-03. `<주제>` — <결정 내용 한 줄> (**D-01 대체**)

**결정일** YYYY-MM-DD · **결정자** <이름> · **경로** 2026-09-09 브리핑 결정 #1

**배경**
- <결정이 필요했던 이유. 브리핑 항목에 적어둔 것>

**결정**
<답에 담긴 내용. 코드로 옮길 수 있게 구체적으로>

**이유**
- <답에 담긴 근거만>

**남는 리스크**
- <답에 언급된 것만. 없으면 이 블록을 빼라>
```

- **답에 없는 「검토했으나 채택하지 않은 대안」·「서버팀 공유 문구」를 만들어 넣지 마라.**
  D-01 에 그 블록이 있는 것은 그때 실제로 검토했기 때문이다
- 답이 `"A 로 갑니다"` 한 줄이면 **결정 + 배경(브리핑의 선택지)** 까지만 쓴다.
  「이유」는 브리핑에 적어둔 추천 근거를 옮기되 **그게 채택 근거임을 명시**한다
- `**경로**` 에 어느 브리핑의 몇 번 항목인지 남긴다. 역추적 경로다

### 3-2. 브리핑 줄에 마커

daily 파일의 해당 `↳ 답:` 줄 **끝에** 추가한다.

```markdown
   ↳ 답: A 로 갑니다 ✅ D-03 기록
```

**멱등 가드로도 쓴다** — 이미 `✅ D-NN 기록` 이 있으면 **다시 기록하지 말고 `applied` 만 찍는다.**
(`_state.json` 쓰기가 실패한 뒤 재실행되는 경우가 이 가드로 잡힌다.)

daily 파일의 **다른 부분은 건드리지 마라.** 그 줄 끝에만 붙인다.

### 3-3. 변경 히스토리 해소 표시

티켓 md `## 변경 히스토리` 에서 **이 결정과 관련된 미처리 `⚠️` 줄**에 `✅` 를 붙인다.

```markdown
- `09-08 16:07` ⚠️ **Confluence** `5919834330` v47 → v48 ✅ D-03 으로 반영
```

- 해소 마커는 **`✅`** 다. `→` 를 쓰지 마라 — 이벤트 본문(`v47 → v48`)과 구분이 안 된다
- **관련 없는 `⚠️` 줄에 `✅` 를 붙이지 마라.** 그 줄이 이 결정으로 풀렸는지 확실치 않으면 그냥 둔다
- 줄을 삭제하지 않는다. append-only 다

## Step 4: 작업이 풀렸으면 이어간다

| 결정의 성격 | 처리 |
|---|---|
| **작업을 풀어준다** (구현 방향이 확정됨) | `ticket-advance` 를 이어 호출한다 |
| **대기·이관·보류** | **기록만 하고 끝낸다. 코드를 건드리지 마라** |

"A 로 갑니다" 는 풀어주는 결정이다. "일단 보류", "BE 에 넘김", "다음 스프린트" 는 아니다.
애매하면 **기록만 하고 끝낸다.** 잘못 구현하는 것보다 안 하는 게 싸다.

`ticket-advance` 를 호출할 때는 **D-NN 을 근거로 명시**한다. 그쪽 Step 1 이 as-is/to-be 를 다시 정리한다.

## Step 5: Slack 보고

**일일 브리핑 스레드에 답글로** 보낸다 (`_state.json["slack"]["ts"]`).
결정 반영은 그날 브리핑의 후속이므로 루트 메시지를 새로 만들 필요가 없다.

```
✅ 결정 반영 2건
• `2026-09-09#1` [shop 3.3.0] <…|CWEB-1547> 배송비 산출 기준 A → **D-03** 기록 (D-01 대체)
  → ticket-advance 이어서 실행 중
• `2026-09-09#2` [shop-admin 3.3.0] <…|CWEB-1548> 노출 시점 보류 → **D-01** 기록만 (코드 미변경)

📄 <obsidian://…|CWEB-1547.md>
```

미응답으로 남은 결정이 있으면 개수만 한 줄 덧붙인다. **재촉 문장을 쓰지 마라.**

## Step 6: `applied` 기록

```json
"decisions": {
  "2026-09-09#1": {
    "...": "...",
    "applied": "2026-09-09T14:12:33+09:00",
    "decision_ref": "CWEB-1547#D-03"
  }
}
```

`applied` 타임스탬프와 어느 D 번호로 갔는지를 같이 남긴다.
`decision_ref` 가 없으면 다음 실행이 "기록은 됐는데 어디에?" 를 다시 찾아야 한다.

## 아무것도 없을 때

응답된 결정이 없으면 **파일도 Slack 도 건드리지 않고** stdout 에 한 줄만 남긴다.

```
응답된 결정 없음 (미응답 2건)
```

빈 실행을 Slack 에 보내지 마라. 그게 알림 피로다.
