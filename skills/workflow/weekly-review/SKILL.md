# weekly-review

## 목적

일일 브리핑은 **오늘**을 본다. 주간 회고는 **한 주가 흘러간 방식**을 본다.
목적은 기록이 아니라 **다음 주에 같은 일이 반복되지 않게 만드는 것**이다.

| 대상 | 기간 | 산출물 |
|---|---|---|
| 직전 **월~일** | 7일 (데이터는 평일 5일치) | `{vault}/weekly/YYYY-Www.md` (ISO 주차) + `{vault}/weekly/_carry.md` |

주차는 **ISO 8601** 로 계산한다 (`date +%G-W%V`). `2026-W37` 형식.
연말·연초에 `%Y` 를 쓰면 주차가 어긋난다. `%G` 를 쓴다.

## 회고가 무의미해지는 지점 — 먼저 이걸 읽어라

이 다섯 개를 어기면 회고는 그 주에 죽는다.

1. **근거 없는 칭찬 금지.** 잘한점에도 **커밋·티켓·날짜**를 붙인다.
   "잘 진행됐다" 는 회고가 아니라 인사말이다.
2. **사람을 평가하지 마라.** 대상은 *일이 흘러간 방식*이다.
   - ❌ "집중력이 부족했다"
   - ⭕ "CWEB-1549 가 22일 멈췄고 원인은 i18n 키 하나였다"
3. **시스템 자신도 회고 대상이다.** 브리핑이 틀리게 짚었거나 감시가 노이즈를 냈으면 **아쉬운점에 적어라.**
   자기 실수를 빼면 회고가 아니라 보고서다.
4. **개선점은 실행 가능해야 한다.**
   - ❌ "더 빨리 하자"
   - ⭕ "`links:` 없으면 `ticket-pull` 에서 경고"

   각 항목에 **`(시스템)` / `(나)`** 를 표시한다. 주체가 없는 개선점은 아무도 안 한다.
5. **데이터가 없으면 없다고 쓴다.** 빈 주를 채우려고 문장을 만들지 마라.

## 경계

- **Jira 쓰기 금지. `git push` 금지. PR 생성 금지.**
- `daily/*.md` 를 **수정하지 않는다.** 지난 주 브리핑은 사실 기록이다
- `daily/releases.md` 쓰기 금지

## Step 1: 상태 갱신

```bash
python3 ~/.local/share/daily-report/poll.py --force
```

**`--force` 가 없으면 주말에는 건너뛴다** (`poll.py` 는 토·일에 즉시 종료한다).
실패해도 계속하되 회고 파일에 ⚠️ 로 남긴다.

## Step 2: 데이터 수집

| 데이터 | 경로 / 명령 | 쓰임 |
|---|---|---|
| 일일 브리핑 5일치 | `{vault}/daily/{월}.md` ~ `{금}.md` | 한 일 · 결정 · 놓친 것의 추이 |
| 이벤트 로그 | `{vault}/daily/_pending.{날짜}.jsonl` (로테이트된 것들) | 변경이 언제 몇 번 왔나 |
| 감시 상태 | `_state.json["watch"]` | 무엇이 몇 일째 걸려 있나 · 이번 주에 해소된 것 |
| 결정 상태 | `_state.json["decisions"]` | 응답률 · 응답까지 걸린 시간 · 미응답 |
| 커밋 | config `repos` 각각 `git log --author=<email> --since='<월> 00:00' --until='<일> 23:59'` | 실제 산출물 |
| Jira | 이번 주 종료된 이슈 · 상태 전이 | 완료 판정의 외부 근거 |
| 티켓 md | `git log`/파일 mtime 기준 변경 히스토리 | 문서가 언제 갱신됐나 |

수집이 부분 실패하면 **그 항목만 `—` 로 두고 진행한다.** 회고 전체를 포기하지 않는다.

## Step 3: 작성

`{vault}/weekly/YYYY-Www.md`. 섹션 순서는 고정이다.

```markdown
---
week: YYYY-Www
range: YYYY-MM-DD ~ YYYY-MM-DD
generated_at: <ISO8601 KST>
commits: <n>
tickets_closed: <n>
decisions_answered: <n>/<n>
watch_red_days: <n>
watch_resolved: <n>
---

# YYYY-Www (MM-DD ~ MM-DD)

## 한 일
## 잘한점
## 아쉬운점
## 개선점
## 다음 주로 넘어가는 것
## 숫자
```

> 각 섹션의 작성 규칙 → `REFERENCE.md`

## Step 4: 개선점을 그 자리에서 반영한다

**개선점을 적어놓고 아무것도 안 바뀌면 회고는 그 주에 죽는다.**

| 주체 | 처리 |
|---|---|
| `(시스템)` | **지금 반영한다.** 스킬 md·설정 임계값 수정 → 항목 끝에 `✅ 반영` + 무엇을 바꿨는지 |
| `(나)` | `{vault}/weekly/_carry.md` 에 적는다 → **다음 월요일 브리핑이 읽어 「네가 할 일」에 올린다** |

`(시스템)` 인데 지금 못 고치는 것(코드 변경이 필요하거나 판단이 갈리는 것)은
`✅ 반영` 을 붙이지 말고 `_carry.md` 로 넘긴다. **거짓 반영 표시가 가장 나쁘다.**

`_carry.md` 는 **누적 파일**이다. 지난 항목을 지우지 말고, 해소된 것에 `✅` 와 해소 주차를 붙인다.

## Step 5: Slack 발송

```bash
python3 ~/.local/share/daily-report/send_brief.py --date <일요일>
```

**루트 메시지로 보낸다.** 일일 브리핑 스레드에 묻히면 주간 회고는 안 읽힌다.

본문은 **잘한점 1~2 + 아쉬운점 1~2 + 개선점 전체**만. 「한 일」과 「숫자」는 파일에서 보게 한다.

> 메시지 포맷 → `REFERENCE.md`

발송 실패해도 회고는 성공이다. 파일 절대경로를 stdout 에 출력한다.

## 재실행

같은 주차를 다시 돌리면 **이미 `✅ 반영` 이 붙은 개선점은 다시 반영하지 않는다.**
`✅ 반영` 마커가 멱등 가드다. `_carry.md` 에 같은 항목을 두 번 적지 마라.
