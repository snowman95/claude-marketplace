# ticket-quiz

**ticket-quiz** — 사용자와 에이전트 사이 **명령 간극**을 줄이기 위해, 현재 작업에 대한 이해도를 시험으로 검증한다.

## 금지

- 시험 전에 정답·해설을 먼저 풀어주지 않는다.
- 시험 중 코드 구현·Plan 수정·커밋하지 않는다.
- 티켓/컨텍스트에 없는 내용으로 엉뚱한 퀴즈를 내지 않는다.

## Step 0: 범위 고정

**완료 기준:** 시험 대상·근거 소스·문항 수가 확정되었다.

1. 아래 순으로 **legwork** — 근거 수집:
   - 현재 브랜치·`git status` (있으면)
   - `tasks/**/*{JIRA-KEY}*.md` · 티켓 md
   - 사용자가 열어둔 HTML/Plan · 최근 대화에서 **결정된 TO-BE**
2. 티켓 키가 없으면 **대화 컨텍스트만**으로 시험 — 범위를 한 줄로 선언한다.
3. 사용자에게 확인 (한 줄):

```
시험 범위: {티켓 또는 주제} · 근거: {파일/대화} · 문항 {8~12}개 · 라운드당 3~4문항
```

사용자가 범위를 바꾸면 Step 0부터 다시.

## Step 1: 루브릭 (내부)

**완료 기준:** must-know 개념마다 최소 1문항이 매핑되었다.

`REFERENCE.md`의 **문항 유형**에서 고른다. 반드시 포함:

- **범위** — 이번 티켓이 바꾸는 것 / 유지하는 것
- **구분** — 비슷한 케이스 2~3개 (예: US→MX vs MX 창고 국내)
- **표기** — 화면 한글 항목명 또는 행 노출
- **함정** — FE/기획에서 자주 혼동하는 분기 1개 이상

루브릭 본문은 사용자에게 보여주지 않는다.

## Step 2: 출제 (라운드)

**완료 기준:** 한 라운드 문항을 모두 제출했고, 사용자 답변을 기다리는 상태다.

라운드마다 **3~4문항**. 형식:

```markdown
## Quiz — {범위 제목}

라운드 {n}/{총 라운드} · 남은 문항 {k}개

### Q{n}.{m}. [{유형}] {질문}

{선지형이면 a/b/c/d — 「기타」항상 포함}
{서술형이면 1~3문장 요구}

---

(다음 문항)
```

- **선지형** — 구분·항목명·범위에 우선 사용.
- **서술형** — 「왜」「어떻게 구분」·함정.
- 문항은 **must-know**에서만; trivia 금지.

한 메시지에 **한 라운드만** 낸다. 답변 전 다음 라운드 금지.

## Step 3: 채점

**완료 기준:** 해당 라운드 전 문항에 대해 ✅/⚠️/❌ 와 한 줄 근거가 있다.

사용자 답변 후:

```markdown
## 채점 — 라운드 {n}

| 문항   | 결과 | 한 줄 피드백 |
| ------ | ---- | ------------ |
| Q{n}.1 | ✅   | …            |

**이번 라운드:** {맞음}/{전체}
```

- ⚠️ — 핵심은 맞으나 용어·범위 하나 틀림.
- ❌ — 케이스 구분·범위 오류. **정답 + 근거(티켓/md 한 줄)** 만 짧게.

채점 후 구현·코드 수정 제안하지 않는다.

## Step 4: 다음 라운드 또는 종료

**완료 기준:** 전체 문항 채점 완료, 또는 사용자가 종료 요청.

- ❌·⚠️가 남았고 문항 여유 있으면 → **약점만** 추가 1라운드 (최대 2라운드 추가).
- 사용자 「그만」「충분」→ Step 5.

## Step 5: Quiz Report

**완료 기준:** 아래 리포트가 출력되었다.

```markdown
## Quiz Report — {범위}

| 구역        | 점수 | 상태     |
| ----------- | ---- | -------- |
| 범위·TO-BE  | …    | 🟢/🟡/🔴 |
| 케이스 구분 | …    | …        |
| 화면 표기   | …    | …        |
| 함정·분기   | …    | …        |

**총점:** {n}/{total} ({%})

### 간극 (명령할 때 헷갈리기 쉬운 점)

- …

### 다음에 이렇게 지시하면 좋음

- 「{구체적 명령 예시}」
```

리포트 후 사용자가 원하면 `grill-me` 또는 `ticket-workflow` Phase 2로 넘길 수 있다고 **한 줄**만 안내.
