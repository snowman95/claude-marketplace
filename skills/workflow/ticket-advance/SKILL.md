# ticket-advance

`ticket-workflow` 를 자동 실행용으로 좁힌 것. Research·Plan 승인 게이트 대신 **중단 기준**으로 안전을 확보한다.

## 절대 규칙

- **`git push` 금지.** 어떤 경우에도 원격에 올리지 않는다. 사람이 확인하고 직접 푸시한다.
- **PR 생성 금지.** `gh pr create` 도 하지 않는다.
- 사람의 일(문의·결정·승인·머지·배포·우선순위)을 대신 하지 않는다. **대신 그 일이 가능한 상태까지 만들어 놓는다.**
- 티켓 범위를 벗어난 파일을 건드리지 않는다.

## 사람에게 넘길 것 / 내가 할 것

| 내가 한다 | 사람이 한다 |
|---|---|
| 문서 읽기·요약·diff 분석 | 외부(기획·디자인·BE) 문의 |
| as-is/to-be 정리 | 스펙 변경 수용 여부 결정 |
| 코드 작성·타입체크·린트 | PR 승인·머지·배포 |
| 자체 리뷰 | 우선순위 재조정 |
| ticket-pull, 커밋 | 푸시 |

"확인해라", "읽어봐라" 를 사람에게 시키지 마라. 그건 내 일이다.

## Step 1: 변경 내용 정리 (as-is / to-be)

대상 티켓의 `links:` 에서 뒤처진 문서를 **실제로 받아서** 읽는다. 버전 숫자만 보고 쓰지 마라.

```bash
python3 ~/.claude/skills/docs-pull-all/scripts/pull.py --ids <page_id> --vault <프로젝트 vault>
```

받은 최신본과 티켓 md의 `## 확정된 스펙` · `## 결정 사항 (Decision Log)` 를 대조해 **코드에 영향 주는 변경만** 추린다.
서식 변경·오타 수정·문구 다듬기는 버린다.

티켓 md의 `## 변경 대응` 섹션에 기록한다 (없으면 `## 변경 히스토리` 앞에 생성):

```markdown
## 변경 대응

### 2026-09-04 · 기획서 v26 → v44

| | 내용 |
|---|---|
| **AS-IS** | 쿠폰 중복 적용 불가. 장바구니 견적 요청 시 최대 1개만 전송 |
| **TO-BE** | v41부터 중복 허용. 배송비 쿠폰과 상품 쿠폰 동시 적용 가능 |
| **근거** | 기획서 v41 「쿠폰 정책」 3-2 |
| **영향 파일** | `src/.../useCartCouponQuote.ts`, `DeliveryCartForm.tsx` |
| **판정** | 🔴 내가 막힘 / 🟡 알아야 함 / ⚪ 무관 (+근거 한 줄) |
| **누가 푸나** | 나 혼자 / 사용자 결정 / 외부 문의 |
```

**영향 없는 변경이면 여기서 끝낸다.** 히스토리 줄에 `→ 영향 없음` 을 붙이고 종료.

## Step 2: 중단 판정 — 두 축으로 가른다

기획서는 FE만 보는 문서가 아니다. 기획·정책·스펙·데이터가 섞여 있다.
변경을 발견했으면 **누구의 문제인지 먼저 가른다.**

### 축 1 — 내 작업이 막혔나

| | 판정 | 행동 |
|---|---|---|
| 🔴 **내가 막힘** | 이 결정이 없으면 **FE 코드를 못 짠다** | 중단. 결정/문의 내용 정리 |
| 🟡 **알아야 함** | 내 작업은 진행 가능하지만 나중에 영향이 온다 | **구현은 계속.** 보고에 참고로 적음 |
| ⚪ **무관** | 정책·데이터·타 파트 영역이고 FE에 안 닿음 | 히스토리에만 남기고 보고에서 뺌 |

⚪ 로 버릴 때는 **왜 FE에 안 닿는지** 한 줄 근거를 남겨라. 근거를 못 쓰겠으면 🟡 이다.

### 축 2 — 누가 풀 수 있나 (🔴 일 때만)

| 주체 | 예 |
|---|---|
| **나 혼자** | 기존 패턴을 보면 답이 나옴 → 중단하지 말고 그냥 하라 |
| **사용자 결정** | 선택지가 둘인데 근거가 없음 |
| **외부 문의** | 기획·디자인·BE에 물어야 답이 나옴 |

**"나 혼자 풀 수 있다"면 중단하지 마라.** 물어볼 것이 없는데 멈추면 자동화가 무의미하다.

### 중단 조건 (🔴 이면서 나 혼자 못 푸는 경우)

- 선택지가 둘 이상이고 문서에 근거가 없음
- 외부에 물어야 답이 나옴
- 기존 `## 결정 사항 (Decision Log)` 과 충돌
- 영향이 티켓 범위를 넘음
- as-is/to-be 를 확정 못 함

중단 시 `## 문의·Blocked` 에 **물어볼 내용만** 적는다. 추측으로 채우지 마라.

```markdown
- **문의 대상**: 기획 OOO
- **문의 내용**: 쿠폰 중복 적용 시 배송비 산출 기준 (A: 최대 할인 / B: 순차 적용). 기획서 v44에 명시 없음
- **기대 해결**: 기준 확정되면 useCartCouponQuote 분기 1곳만 수정하면 됨
```

Slack에 `⏸ 중단` 보고 후 종료. **Step 3 이하로 가지 않는다.**

## Step 3: 워크트리

`worktree` 스킬을 호출한다. 위치는 **`.claude/worktrees/{브랜치명의 / 를 + 로}`**.

```
features/CWEB-1547 → .claude/worktrees/features+CWEB-1547
```

이미 그 브랜치의 워크트리가 있으면 **재사용한다.** 새로 만들지 마라.
메인 체크아웃이 이미 그 브랜치면 워크트리를 만들지 않고 그대로 쓴다.

## Step 4: 브랜치

| 티켓 | 접두사 |
|---|---|
| CWEB (기능) | `features/` |
| WPQ (QA 버그) | `fix/` |
| 그 외 | 기존 브랜치가 있으면 그 규칙, 없으면 `fix/` |

- **기존 브랜치가 있으면 checkout.** 이름이 달라도(`feat/`·`features/` 혼재) 그 티켓 전용이면 그걸 쓴다
- 없으면 `origin/develop` 베이스로 생성. `git fetch origin` 먼저
- fixVersion이 `3.0.0` 계열이면 베이스가 다르다 → `ticket-commit` 의 `REFERENCE.md` 표를 따른다

## Step 5: 구현

Step 1의 「영향 파일」만 고친다. 범위를 넓히지 마라.

- 기존 코드 패턴을 그대로 따른다
- `any`·`unknown` 금지
- 로케일에 없는 문구는 키를 새로 만들지 말고 하드코딩 + `// FIXME 다국어 업데이트 필요`
- 불필요한 주석·JSDoc 금지

## Step 6: 자체 리뷰

**cwd 를 워크트리 루트로 옮긴 뒤** 실행한다. 메인 리포에서 워크트리 경로를 지정해도 동작하지만, 경로가 섞이면 대상이 헷갈린다.

### 6-1. 툴링 (먼저)

`code-review` 스킬은 "툴링이 강제하는 것은 건너뛴다"는 방침이라 **타입체크·린트를 대신해주지 않는다.** 직접 돌린다.

```bash
npm run type-check     # tsc --noEmit -p tsconfig.json
npm run lint           # eslint src/
```

깨지면 **고치고 다시 돌린다.** 깨진 채로 Step 7로 가지 않는다. 고칠 수 없으면 중단하고 보고한다.

### 6-2. code-review 스킬

`code-review` 를 호출하되 **인자를 반드시 명시한다.** 생략하면 스킬이 사람에게 되묻고 자동 실행이 거기서 멈춘다.

| 인자 | 값 |
|---|---|
| 고정점(fixed point) | 구현 시작 직전 커밋 SHA. 브랜치를 새로 판 경우 `origin/develop` |
| spec 경로 | 티켓 md 절대경로 (vault). `## 변경 대응` 의 as-is/to-be 가 spec 이다 |

호출 예:
```
/code-review <구현직전SHA> spec=<vault>/myproject/tasks/shop3.3.0/CWEB-1547.md
```

> 이 리포에는 `CLAUDE.md`·`CONTRIBUTING.md`·`CODING_STANDARDS.md` 가 **없다.**
> 따라서 Standards 축은 Fowler 스멜 베이스라인만으로 돌아간다. 리포 표준 위반은 나오지 않는다.
> `docs/agents/issue-tracker.md` 도 없으므로 **spec 경로를 반드시 넘겨야** Spec 축이 산다.

### 6-3. 스택 특화 리뷰

Standards 축이 얇으므로 `weverse-web-developer:review:typescript-reviewer` 서브에이전트를 하나 더 돌린다.
보안에 닿는 변경(인증·결제·외부 입력)이면 `security-sentinel` 도 추가한다.

### 6-4. 스스로 점검

도구가 못 잡는 것만 본다.

- Step 1의 TO-BE를 실제로 달성했는가
- `git status` 에 의도치 않게 건드린 파일이 있는가
- 기존 `## 결정 사항 (Decision Log)` 과 어긋나는 구현을 하지 않았는가
- **내가 확신 못 하는 지점** — 숨기지 말고 보고에 `⚠️` 로 적는다

## Step 7: 커밋

`ticket-commit` 스킬 규칙을 따른다. **`--no-verify` 금지** — 훅이 돌아야 검증이 된다.

```
{type}({scope}): {요약} ({JIRA-KEY})
```

푸시하지 않는다.

## Step 8: 보고

Slack으로 검토 요청. 포맷 → `REFERENCE.md`

**사람이 할 일을 번호로 명시한다.** "확인 바랍니다" 같은 말은 쓰지 않는다.
